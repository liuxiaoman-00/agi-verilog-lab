## 一、它解决什么问题

数字逻辑设计是电子类专业的核心基本功，但「写完一段 HDL，怎么确认它真的对」长期依赖
人工写测试台——既慢，又因人而异，还常常覆盖不到边界。

本项目把这件事做成一个**不需要人工写任何测试用例**的闭环：

```
功能规格 ──► AGH 规划 ──► Agnes 模型生成 Verilog ──► 自动搭建等价性测试台
        ──► iverilog 编译 + vvp 仿真 + yosys 综合 ──► 逐向量比对参考实现
        ──► 失败则自动分类 ──► 按类给出修复策略 ──► 重新生成（最多 N 轮）
```

关键在于：**评判对错的标准不是人，也不是模型自己，而是一条与生成过程完全独立的
验证链路**——编译器、仿真器、综合器和参考实现。因此结论是可复核、可复现的。

## 二、为什么「验证」这件事要先自证

一个会误判的裁判，给出的「通过」毫无价值。所以项目里有一个 `selfcheck` 环节，
**先用已知缺陷去校准裁判本身**，再让裁判去评判模型：

| 校准项 | 做法 | 结果 |
|---|---|---|
| 参考实现自校准 | 把 13 个人工参考实现改名后当作候选提交，必须全部判定通过 | 13/13 |
| 已知缺陷检出 | 注入 7 个事先标注类别的缺陷，必须被判成**标注的那一类** | 7/7 |

注入的缺陷覆盖：语法错误、接口违规、组合逻辑分支不完整（推断出锁存器）、
输出节拍错位、边界语义写错（仅 a==b 时暴露）、移位方向错误、使能优先级错误。

## 三、快速开始

### 1. 环境

```bash
# Python 3.9+ 即可，核心链路零第三方依赖
python -V

# EDA 工具链（iverilog / vvp / yosys）：解压 oss-cad-suite 到本地任意位置
#   https://github.com/YosysHQ/oss-cad-suite-build/releases
# 代码会自动逐级向上寻找 tools/oss-cad-suite，无需配置环境变量
```

> **Windows 注意事项（重要）**
> - oss-cad-suite 的 DLL 在 `lib/` 子目录，`EDABackend.env()` 会把 `bin` 与 `lib`
>   一并加入子进程 PATH；少了 `lib` 会直接 `0xC0000135` 崩溃。
> - **项目的所有路径必须是纯 ASCII**。iverilog 的预处理器处理含中文的路径会报
>   `Invalid argument / Preprocessor failed`。

### 2. 不需要 API Key 也能先跑通

```bash
python run.py --list        # 查看 13 条规格
python run.py --selftest    # 元验证 + 以参考实现替代模型走完整闭环
```

`--selftest` 会用人工参考实现充当「模型输出」，用来验证工具链和闭环逻辑是否通畅。
它**不是模型**，也不产生任何评测数据。

### 3. 接入 Agnes 模型后正式评测

```bash
export AGNES_API_KEY=<赛事官方群发放的 Key>
python run.py --all                       # 全部规格
python run.py --spec seq1011 traffic      # 只跑指定规格
python run.py --all --max-attempts 6      # 调整修复轮数
```

## 五、AGH 在哪里

本项目以 **Agnes Harness（AGH）** 为智能体运行与执行底座。工具层通过 **MCP** 暴露：

```bash
python -m vlab.mcp_server          # 以 stdio 方式提供 MCP 服务
```

暴露的工具共四个：

| 工具 | 作用 |
|---|---|
| `list_specs` | 列出全部规格的接口契约与激励策略，供 AGH 做任务规划 |
| `verify_candidate` | 对候选 Verilog 执行「编译 → 仿真 → 综合 → 逐向量比对」并返回裁决 |
| `describe_verdict` | 解释裁决字段含义，供 AGH 选用修复策略 |
| `stimulus_info` | 返回某条规格的激励构造方式与向量规模 |

AGH 负责串联「任务规划 → 能力调用 → 反馈处理 → 结果验证」四个环节，
每一次工具调用的入参、出参、耗时都被记录进 `runs/` 下的裁决流水，
这些流水即提交材料中的「AGH 执行记录」与「工具调用链」证据。

由于工具层与本体的耦合被刻意做成「可脱离 AGH 独立运行」，
在没有 AGH 的环境里也能用 `run.py` 复现完全相同的判定结果。

## 六、激励策略的两点讲究

1. **组合逻辑：穷举**。输入空间 ≤ 2^11 的全部规格都做完整穷举（如 alu4 为 2048 个向量），
   覆盖率 100% 是**结论而不是估计**。
2. **时序逻辑：de Bruijn 序列**。串行激励改用 de Bruijn 序列 B(2, k)，
   保证任意长度 k 的输入序列都出现过。对移位寄存器、序列检测器、FSM 这类
   **顺序敏感**的电路，随机激励覆盖不到长模式，而 de Bruijn 序列可以在
   「k 阶窗口」意义上给出严格保证。

## 七、失败分类学

| 类别 | 含义 | 修复策略要点 |
|---|---|---|
| `SYNTAX` | 编译失败 | 喂编译器原文 |
| `INTERFACE` | 端口名/方向/位宽与规格不符，或用了被禁的 parameter | 逐项列出差异 |
| `LATCH` | 综合后推断出锁存器（组合逻辑分支不完整） | 补 default / 先赋默认值 |
| `TIMEOUT` | 仿真超时，疑似组合反馈环 | 检查无寄存器自反馈 |
| `RESET` | 复位释放后输出仍为不定态 X | 检查复位分支覆盖 |
| `TIMING_SHIFT` | 逻辑正确但节拍超前/滞后（±N 拍） | 超前→改寄存输出；滞后→去掉多余一级 |
| `VALUE_MISMATCH` | 存在与参考不一致的输入向量 | 喂反例向量表 |

`TIMING_SHIFT` 是本项目特意做出来的一类：很多实现**逻辑完全正确，只是输出晚/早一拍**。
若只做逐拍严格比对，它会被误判成功能错误，修复建议也就跟着跑偏。
这里会对两条轨迹做 ±N 拍的平移重比对，把它单独识别出来。

## 八、测试样例的分类（正常 / 边界 / 失败）

- **正常**：13 条规格中组合逻辑穷举通过、时序逻辑 de Bruijn 激励通过。
- **边界**：激励构造中专门包含全 0、全 1、走 1、走 0、相邻位翻转等边界向量；
  `cmp4` 的 `>=` 缺陷正是由 a==b 这一类边界向量才暴露出来。
- **失败**：`selfcheck` 注入的 7 个已知缺陷，每条都有完整的失败→诊断→结论记录。
